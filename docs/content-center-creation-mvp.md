# Создание контента — реализация ТЗ

Источник: https://wispo-agency.notion.site/3d99523e994e80a6964ac056e8f2d360
Редакция Notion: 18.09.2026. Текст требований прочитан полностью; прототипы — ориентир, не замена требований.

## Границы

Раздел принадлежит workspace, не отдельному сайту. Рабочая единица — кластер;
у него независимые статьи для подключённых площадок. AI-провайдер пока не
подключаем и не подменяем генерацию фиктивными результатами.

Площадки MVP — сайты этого workspace с CMS статей. Внешние площадки требуют
отдельных адаптеров публикации. Постоянные правила храним отдельно от разовой
инструкции/файла запуска. Источники для SEO-кластеризации и законченные результаты
исследований предыдущим ТЗ ещё не определены: не выдаём подтверждённые ссылки
исследования за его выводы. Нужны явные точки интеграции этих данных.

## Приёмка

- [ ] Единая таблица актуальных и архивных кластеров, поиск, фильтры направления,
  статуса и рекомендации по площадкам; выбор актуальных кластеров.
- [ ] Нулевой выбор означает все актуальные кластеры, а не только отфильтрованные.
- [ ] Страница кластера: запросы и частотности, основной запрос, статьи/назначение/
  обоснования, ссылки на общую историю.
- [ ] Запуск: автоматический workspace-контекст, постоянные правила, разовая
  инструкция, список промптов, разовый файл; прогресс реальных операций и ошибки.
- [ ] Раздельные статус статьи и рекомендация. Повторный запуск не проверяет
  снятые статьи и статьи с незавершёнными предложениями.
- [ ] Корректировка всей статьи/элемента/фрагмента; голос, промпты, файл;
  предложения Было → Стало, отдельные решения, одна версия после всех решений.
- [ ] Текущая и опубликованная версии независимы; непринятые предложения не
  изменяют текст, новые версии не публикуются автоматически.
- [ ] Публикация текущей версии в CMS выбранного сайта/раздела, сохранение URL
  при том же месте публикации; отдельное снятие с публикации.
- [ ] История запусков без раскрытия; неизменяемые события кластеров/статей;
  поиск/период/пользователь/тип, контекст кластера.
- [ ] История версий с различиями и безопасным восстановлением новой версией.
- [ ] Авторизация workspace на каждом запросе, optimistic concurrency,
  транзакционная публикация, защита от двойного запуска и устаревшего AI-ответа.

## Порядок

1. Аддитивная схема и доменные операции; provider-neutral AI-контракт.
2. Связанные экраны внутри существующей оболочки CMS, на всю ширину.
3. Изолированные проверки БД и точечные проверки UI/типов.
4. Отдельная feature-ветка, резервная копия, релиз на действующий сервер,
   проверка встроенным Browser. `main` и checkout коллеги не изменяем.

Риск: Tier 2 — новые данные, изоляция workspace, конкурентные изменения и
публикация. Проверки сосредоточены на этих контрактах, без расширения задачи
до переработки других разделов.

## Реализовано, 19.09.2026

Все перечисленные экраны и доменные операции реализованы. Добавлены также
ручной ввод подготовленных кластеров, разделение/объединение с сохранением
исходных запросов и связей в истории. Это не автоматическая SEO-кластеризация.

Таблица, настройки, кластер, история, статья и история версий находятся внутри
существующей оболочки CMS (`cc=creation`). История запусков не раскрывает строки;
прогресс и ошибки отдельных операций отображаются в рабочем экране запуска.
История запусков содержит производство, не технические задания корректировки.

Публикация транзакционно создаёт/обновляет запись в существующей CMS статей и
её журнале. Текущая версия Контентного центра не копируется в CMS сайта до
отдельного действия пользователя. При изменении связанной статьи коллегой
непосредственно в CMS сайта повторная публикация блокируется конфликтом, а не
перезаписывает его текст. Сайт публикации закреплён за статьёй площадки;
для другой площадки существует самостоятельная статья кластера.

## Подключение AI (остаётся отдельным этапом)

Нужно зарегистрировать `CREATION_PROVIDER` с реализацией `CreationProvider`.
Провайдер получает структурированный `CreationAiInput`, возвращает структурированный
ответ: релевантность, рекомендацию и обоснование, новый документ либо предложения.
SDK и поставщик не выбраны. Без адаптера реальные API не вызываются; фиктивного
успеха и статей в production нет. Установка одного ключа без адаптера недостаточна.

Файлы до 10 МБ передаются только адаптеру с `supportsFiles`; файл и снимок контекста
удаляются из записи после завершения/ошибки. Сохраняются инструкция, имя файла,
автор, итоги операций. При повторе файл нужно прикрепить заново. Автоматического
повтора оплачиваемого AI-запроса после сбоя нет: пользователь запускает повтор
неудачных операций; успешные не дублируются. Истёкшие задания фиксируются ошибкой.

Контекст автоматически собирается только из этого workspace: последняя
обработанная информация, текущие кластеры, существующие статьи сайтов и
Контентного центра, правила проекта и площадок, разовая инструкция и файл.
`researchResults` пока пуст: предыдущий исследовательский раздел фиксирует
источники, но ещё не производит утверждённые результаты исследования. Их нельзя
подменять списком ссылок. Внешние площадки и получение их актуальных материалов
потребуют соответствующих адаптеров; в данном MVP площадки — сайты Wispo CMS.

## Проверки

- 10 интеграционных сценариев PostgreSQL в отдельной локальной схеме: ACL,
  устаревшие изменения, контекст/файл, повтор ошибок, корректировки, публикация,
  восстановление, неизменная история, разделение/объединение и отключённый AI.
- 4 теста состояния/фильтров создания; 2 проверки HTML статьи/истории.
- 3 теста общей навигации и 6 проверок ранее реализованной подготовки/диктовки.
- Проверка типов API/web и ESLint затронутых файлов.
- Production-сборка и проверка действующего сайта — в записи выпуска.
