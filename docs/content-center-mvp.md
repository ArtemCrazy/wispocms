# Контент-центр: первый этап MVP

Рабочая ветка: `feature/content-center-preparation-mvp`, основание: `b700a05` (`origin/main` на 19.09.2026).

Изолированная рабочая копия не меняет папку коллеги. Ветка публикуется отдельно; слияние в `main` и выкладка на общий сервер не входят в этот этап. Локальные неопубликованные изменения другого разработчика через GitHub не видны.

## Объём

Первый законченный сценарий: рабочее пространство → Контент-центр → Подготовка информации → материалы и инструкция → обработка → документ → история и восстановление версии.

Источники:
- https://wispo-agency.notion.site/AI-3cf9523e994e807c909ddfdebf01a24b
- https://wispo-agency.notion.site/3d89523e994e80b3bb10c584f707994e

Исследования, кластеры, генерация статей, публикация и клиентские брифы остаются следующими этапами. Существующая медиатека сохраняется отдельно от AI-процесса. Документ подготовки не является ручным редактором. Промпт копируется в инструкцию; изменение инструкции не изменяет сохранённый промпт.

## Правила

- Данные и доступ ограничены рабочим пространством.
- Успешная обработка создаёт новую версию; ошибка сохраняет прежний результат.
- Восстановление создаёт новую версию без изменения исторических документов.
- Материалы автоматически включаются в обработку; без материалов требуется явный выбор соответствующего сценария.
- Нельзя выдавать тестовый или шаблонный ответ за реальную работу AI. При отсутствии настройки провайдера интерфейс сообщает об этом.
- По уточнению пользователя API пока не подключается. Обработка строится вокруг интерфейса `PreparationProvider`; поставщик (DeepSeek, OpenAI или другой) выбирается позже. Никаких вызовов внешней модели и зависимостей её SDK в этой версии.
- Для первой поставки набор форматов источников явно показывается в интерфейсе; неподдерживаемые форматы не считаются обработанными.
- Изменения схемы добавляются отдельной миграцией, без редактирования применённых миграций.

## Проверка

Проверить изоляцию workspace, входные ограничения, успешный/неуспешный запуск, повторное выполнение, сохранение и восстановление версий. Выполнить сборку затронутых приложений и доступную визуальную проверку в браузере. Фактическую готовность AI-провайдера и окружения указать в итоговом отчёте.

## Где находится реализация

- `apps/api/src/content-center` — защищённые workspace API, источники, черновик, промпты, очередь и версии.
- `apps/api/src/database/migrations/1790020800000-ContentCenterPreparation.ts` — только новые таблицы `cc_*`; существующие данные сайтов не меняет.
- `apps/web/src/app/content-center` — корневой экран, подготовка, диалоги, документ и история.
- `apps/web/src/app/page.tsx` — вход «Контент-центр» под рабочим пространством. Старый раздел файлов обозначен «Медиатека».

## Подключение AI позже

Реализовать серверный `PreparationProvider` и зарегистрировать его под токеном `PREPARATION_PROVIDER` в `ContentCenterModule`. Договор адаптера:

1. Стабильное `name` идентифицирует адаптер для очереди. `generate` принимает `instruction`, `context.materials`, `context.previousResult`, `signal` и возвращает `{ content: string }`.
2. Результат — один Markdown-документ (заголовки, абзацы, списки, таблицы), без отдельного резюме и без HTML. Нельзя придумывать отсутствующие факты: пробелы обозначаются вопросами. Содержимое источников является данными, а не системными инструкциями; адаптер должен явно разделять их в запросе к модели.
3. Ключи, модель и адрес API задаются только на сервере. Секреты и подробности ошибок провайдера не возвращаются клиенту.
4. Адаптер обязан поддерживать отмену через `signal`; сервис также ограничивает ожидание 180 секундами. Автоматического повтора платного запроса нет. Оборванные задачи переходят в ошибку через 5 минут, невыбранные задачи очереди — через 30 минут.
5. Материалы фиксируются во временном контексте при запуске. После успеха или ошибки этот контекст удаляется. Это не постоянный паспорт источников версии.
6. Новый результат записывается атомарно с завершением задачи. Восстановление V1 после V2 создаёт V3. Исторические результаты не переписываются.

В поставке нет рабочего адаптера, SDK и обращений к модели. Подключение означает реализацию этого небольшого адаптера и его проверку, а не только вставку API-ключа. Очередь, UI и модель версий уже готовы. Тестовый адаптер существует только в тестах, не включается переменными окружения в работающей CMS.

## Границы первой поставки

Поддерживаются введённый текст, TXT/Markdown в UTF-8 и текст одной публичной HTTPS-страницы. До 50 материалов по 40 000 символов, до 100 промптов, инструкция до 12 000 символов. Суммарный контекст с предыдущим результатом — до 180 000 символов; превышение отклоняется, не обрезается незаметно. Документ — до 80 000 символов.

Импорт URL блокирует внутренние сети/IP-адреса, фиксирует проверенный DNS-адрес на соединение и повторно проверяет каждый редирект. Это не обход сайта и не браузерный парсер. PDF, DOCX, изображения/OCR, аудиофайлы и голосовой ввод пока не реализованы. Редактирование/удаление библиотеки промптов, исследования, генерация статей и публикация не входят в этот этап. Сохранение источников и инструкции — явными кнопками, не автосохранением.

## Проверка разработчиком

В `apps/api`:

```powershell
pnpm build
pnpm exec eslint src/content-center src/database/migrations/1790020800000-ContentCenterPreparation.ts
# Только отдельная локальная PostgreSQL-база с именем, оканчивающимся на _tests:
$env:CONTENT_CENTER_TEST_DATABASE_URL = '<локальный URL тестовой БД>'
pnpm exec jest --runInBand --runTestsByPath src/content-center/content-center.integration.spec.ts src/content-center/preparation-ai.service.spec.ts src/content-center/public-material.spec.ts
```

Интеграционные тесты создают уникальную схему внутри тестовой базы и удаляют только её. Без `CONTENT_CENTER_TEST_DATABASE_URL` они явно пропускаются. Проверяются доступы, оптимистичные версии правок, конфликт двух запусков/воркеров, фиксация входных материалов, ошибки, история и восстановление.

В `apps/web`: `pnpm exec next typegen`, `pnpm exec tsc --noEmit`, `pnpm exec eslint src/app/content-center src/app/page.tsx src/app/media-view.tsx`, `node --test test/workspace-media-domain.contract.test.mjs test/content-center-document.test.mjs`. Тест документа проверяет Markdown-структуру и отсутствие исполняемого HTML из ответа модели.

Браузерный сценарий: войти → открыть пространство → Контент-центр → Подготовка информации → сохранить источник → создать промпт → использовать и отредактировать его копию → сохранить задачу → перезагрузить страницу. Источник и задача должны остаться, исходный промпт не должен измениться; кнопка обработки без адаптера недоступна.

Для локальной проверки использована отдельная пустая PostgreSQL. Старые миграции импорта Armaturex/Skinova зависят от клиентских данных; в **локальном UI-стенде** они исключены, а не изменены или помечены выполненными на общем сервере. Подключаться для тестов к production-базе нельзя. Полную выкладку приложения этот этап не проверяет.

## Совместная работа

Брать ветку `feature/content-center-preparation-mvp` из GitHub. Перед слиянием обновить `origin/main`, разрешить возможные пересечения в `page.tsx`, `app.module.ts` и списке миграций. Не делать force-push в общие ветки. Проверить, что у коллеги нет параллельной миграции с тем же номером. Развёртывание и применение миграции на общем сервере — отдельный согласованный шаг после просмотра MVP.
