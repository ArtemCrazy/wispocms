# Wispo CMS: TemplatePackage и frontend-релизы

Дата: 02.10.2026. Статус: согласованная архитектура этапа Template SDK.
Ветка: `codex/access-control-v2`. Выкладка и изменения `main` не выполняются.

## Цель

Связать CMS с конкретной проверенной сборкой React-сайта так, чтобы исходный
код оставался в Git, а CMS знала доступные шаблоны, их схемы и точную версию
frontend. Регистрация кандидата выполняется автоматически доверенным CI/CD или
локальной служебной командой. Администратор Wispo не загружает manifest вручную.

Решение реализует этап 4 ТЗ: TemplatePackage версионируется, CMS знает текущую
фактически развёрнутую версию сайта и совместимые кандидаты, а preview и public
внутри одной сборки используют один renderer. Физическое переключение между
неизменяемыми build-артефактами относится к следующему этапу публикации.

## Вне объёма этого этапа

- перенос Skinova в отдельный Git-репозиторий;
- самостоятельный production-деплой frontend из CMS;
- полноценная очередь статической сборки и CDN switch;
- активация кандидата, атомарное переключение и rollback frontend-кода;
- редактор HTML, JSX, CSS или JavaScript;
- создание нового визуального block-builder;
- автоматическая генерация manifest AI-агентом;
- массовое обновление нескольких сайтов одной кнопкой.

Эти функции могут опираться на создаваемый контракт, но не нужны для проверки
первой версии на локальном Skinova.

## Принятый вариант

Используется manifest-driven реестр. Manifest является JSON-контрактом между
репозиторием сайта и CMS. JSX, CSS, функции и сборочные исходники в него не
входят.

Отклонены два альтернативных варианта:

1. Ручное заведение релиза в админке — создаёт лишнюю работу и риск расхождения
   введённой версии с фактической сборкой.
2. Runtime-интроспекция уже опубликованного сайта — обнаруживает контракт
   слишком поздно и не позволяет надёжно проверить кандидата до переключения.

## Термины и независимые версии

- `manifestVersion` — версия формата самого manifest.
- `packageId` — постоянный машинный ключ frontend-пакета, например
  `skinova-media`.
- `packageVersion` — уникальная версия готовой сборки пакета, явно указанная в
  versioned manifest template. При изменении runtime её нужно повысить;
  конфликт digest защищает от случайного повторного использования номера.
- `sourceRevision` — точный Git commit/tag исходного кода.
- `releaseDigest` — детерминированный digest входов релиза, manifest и
  скомпилированного runtime-каталога текущего этапа.
- `artifactDigest` — необязательный digest физического неизменяемого
  build-артефакта. До реализации этапа 5 остаётся `null`.
- `template.version` — версия контракта данных конкретного шаблона или
  компонента.
- CMS revision — версия значений контента конкретной сущности.

Изменение CSS или внутреннего JSX создаёт новый frontend-релиз, но не обязано
менять `template.version`. Несовместимое изменение полей требует новой версии
контракта шаблона. Изменение заголовка баннера создаёт только новую CMS-ревизию
данных и не создаёт новый frontend-релиз.

## Manifest TemplatePackage

Минимальный JSON-контракт:

```ts
type TemplatePackageManifest = {
  manifestVersion: 1;
  packageId: string;
  packageVersion: string;
  title: string;
  siteType: "media" | "corporate" | "ecommerce" | "landing";
  cmsApi: {
    minSchemaVersion: string;
    maxSchemaVersion?: string;
  };
  source: {
    repository: string;
    revision: string;
  };
  build: {
    releaseDigest: string;
    artifactDigest?: string;
    builtAt: string;
    runtimeMode: "embedded-next" | "external";
    runtimeUrl?: string;
  };
  templates: Array<{
    kind:
      | "homepage"
      | "articles_list"
      | "article"
      | "category"
      | "header"
      | "footer"
      | "system_page";
    key: string;
    version: string;
    title: string;
    dataScope: "cms-entity";
    runtimeContext: TemplateRuntimeContextKey[];
    dataSchemaVersion: string;
    dataSchema: Record<string, unknown>;
    configSchema?: Record<string, unknown>;
    slots?: Array<{
      key: string;
      title: string;
      renderer: string;
      placement: string;
      maxItems?: number;
    }>;
  }>;
};
```

Manifest Skinova описывает существующие ключи `skinova-home@1`,
`skinova-editorial@1`, `skinova-article@1`, `skinova-category@1`,
`skinova-header@1`, `skinova-footer@1`, системный `skinova@1` и renderer keys
баннеров. Он становится единственным декларативным каталогом возможностей
Skinova; runtime registry отдельно связывает эти ключи с React-компонентами.

`dataSchema` и `configSchema` описывают только сохраняемые и редактируемые в CMS
данные сущности, но не весь объект props React-компонента. Неперсистентный
контекст route-адаптера (`siteSlug`, коллекции связанных сущностей, баннеры,
globals/layout и media URL) перечисляется отдельно в `runtimeContext` и не
раздувает entity schema. В Task 2 адаптер собирает component props из
прошедших schema-проверку entity data и отдельно загруженного runtime context.
Ключи `runtimeContext` выбираются только из типизированного словаря контракта и
совпадают с фактическими props renderer (`related`, `promo` и т. п.). Адаптеры
Task 2 обязаны потреблять именно объявленные ключи и явно преобразовывать в них
API/route-данные, не вводя неописанные строковые псевдонимы.

## Хранение в CMS

Добавляются три уровня данных.

### TemplatePackage

Платформенная сущность с постоянным `packageId`, названием, типом сайта и URL
репозитория. Один пакет может иметь несколько неизменяемых версий и в будущем
использоваться несколькими совместимыми сайтами.

### TemplatePackageVersion

Неизменяемая зарегистрированная версия: номер пакета, Git revision, digest,
manifest, диапазон поддерживаемых CMS API и данные build/runtime. Повторная
регистрация того же `packageId + packageVersion + releaseDigest` и того же
canonical manifest идемпотентна. Попытка зарегистрировать тот же номер версии
с другим digest или manifest отклоняется. Неизменяемость защищается не только
сервисом, но и DB-trigger, запрещающим UPDATE immutable-полей версии.

### Текущая развёрнутая версия сайта

Сайт хранит nullable-ссылку на пакет и его версию, которая фактически находится в его
текущей frontend-сборке. Это диагностическая привязка, а не маршрутизатор кода.
После успешной выкладки доверенный deploy-процесс отдельным служебным запросом
сообщает CMS уже развёрнутую версию. Кандидаты, зарегистрированные до выкладки,
не меняют эту ссылку автоматически.

Существующая таблица `site_content_templates` остаётся активным каталогом
шаблонов конкретного сайта. Регистрация, preflight и deploy-report не создают,
не удаляют, не деактивируют и не переназначают его строки. Связь каталога с
пакетом и его синхронизация войдут в следующий этап вместе с реальным
переключением build-артефакта.

## Регистрация из CI/CD

Промежуточные Git-коммиты CMS не регистрирует. После успешной сборки и тестов
CI вызывает служебный endpoint и передаёт manifest. Endpoint защищается
отдельным release token из окружения; токен не хранится в БД, Git или manifest,
не возвращается в API и не попадает в логи.

Локальная служебная команда читает тот же manifest Skinova и вызывает тот же
контракт регистрации. Отдельная команда preflight проверяет совместимость до
выкладки. Ещё одна отдельная команда report-deployed вызывается только после
того, как оператор или pipeline действительно проверил обслуживаемую сборку.
Регистрация сама по себе никогда не вызывает report-deployed. Команды
моделируют будущий build/deploy pipeline и не создают отдельной бизнес-логики.

Регистрация:

1. проверяет структуру и допустимые значения;
2. запрещает повторяющиеся `kind + key + version` и renderer keys;
3. проверяет диапазон CMS API;
4. проверяет отсутствие исходного кода и исполняемых значений;
5. вычисляет/проверяет неизменяемую идентичность версии по release digest и
   canonical manifest;
6. создаёт кандидата либо возвращает уже существующий идентичный результат;
7. не меняет текущую версию сайта и публичный контент.

Невалидный кандидат не сохраняется как доступный релиз.

Read-only preflight принимает только уже зарегистрированную версию и до
выкладки проверяет тип сайта, текущие назначения и наличие embedded runtime.
Служебный отчёт после выкладки связывает сайт с пакетом и фактически
развёрнутой версией, но не меняет каталог. Если состояние после выкладки
оказалось несовместимым, pointer всё равно фиксирует факт, а read API возвращает
статус рассинхронизации и безопасный список причин вместо ложной старой версии.
Оба действия доступны только release pipeline и не являются пользовательскими
кнопками.

## Текущая версия, кандидаты и preview

Страница «Шаблоны» сайта показывает текущую развёрнутую версию пакета.
Администратор Wispo дополнительно видит зарегистрированные совместимые
кандидаты того же `TemplatePackage`, статус «зарегистрирован», Git revision и
release digest. Для legacy-сайта без привязанного пакета список кандидатов
пуст. Владелец сайта
видит только текущий пакет и продолжает назначать уже доступные шаблоны;
контент-менеджер не получает управление frontend-релизами.

Для текущего `embedded-next` Skinova доступен обычный preview текущей сборки.
Новый embedded-кандидат нельзя считать просмотренным, пока его код не развёрнут
в отдельном preview-окружении. Для `external` кандидат может содержать
проверенный CI адрес `runtimeUrl`; тогда CMS показывает ссылку на этот preview.

Кнопок «Активировать» и «Rollback» на этом этапе нет. Их появление допустимо
только после реализации неизменяемых артефактов и маршрутизатора, который
действительно способен оставить старый код активным или вернуть его.

## Runtime registry React

React-часть содержит два согласованных слоя registry. Обычный `.ts`-каталог
связывает package-aware identity
`packageId + packageVersion + kind + key + templateVersion` с runtime-
возможностью и доступен проверкам без загрузки JSX. Отдельный `.tsx`-слой
связывает только самостоятельные component surfaces с React-компонентами.
`homepage`, `article`, `category` и `system_page` имеют самостоятельные
component surfaces; `articles_list` встроен в `skinova-home`, а `header` и
`footer` встроены в общий `skinova-chrome`, поэтому не маскируются под
несуществующие отдельные компоненты. Slot identity дополнительно включает
`packageId + packageVersion + rendererKey`. Manifest остаётся полностью
сериализуемым. Все публичные и CMS-preview состояния текущего общего embedded
route разрешают runtime-возможность через один каталог, а не через
разрозненные `if` и строковые switch.

Registry обязан доказать тестами, что:

- каждый шаблон manifest имеет runtime-возможность с правдивым component или
  integrated binding;
- неизвестная комбинация `key/version` не рендерится молча через Skinova;
- banner renderer из слота существует;
- preview и public выбирают одинаковый renderer;
- в сериализуемый manifest не попадают React-компоненты и функции.

## Публичный контракт

`/api/public/sites/:slug/manifest` дополняется:

- идентификатором текущего развёрнутого TemplatePackage и его версии;
- `sourceRevision`, `releaseDigest` и nullable `artifactDigest` без секретов;
- поддерживаемыми template assignments;
- полями `displayTemplateKey`, `displayTemplateVersion`,
  `displayTemplateConfig`, `systemTemplateKey` и `systemTemplateVersion` в
  описании content model.

Это позволяет отдельному React-репозиторию проверить, что CMS отдаёт данные в
ожидаемом контракте.

## Совместимость и миграция

Миграция только добавляет таблицы, trigger неизменяемости и nullable-ссылки. Применённые миграции не
редактируются. Она не выдумывает commit или digest уже установленной сборки и
не меняет пользовательские данные. После запуска нового кода локальная
CI-like команда идемпотентно регистрирует фактический manifest Skinova и
сообщает CMS текущую развёрнутую версию. Другие сайты остаются с `NULL` и
продолжают использовать прежний каталог без новой блокировки. История
активаций на этом этапе не создаётся.

Новый код должен поддерживать legacy-сайт без текущего package до его явной
регистрации. Откат приложения не откатывает БД автоматически. `down()` удаляет
только новые связи/таблицы при отсутствии зависимостей; на внешнем окружении
разрушительный down не запускается вместо штатного восстановления.

## Ошибки и безопасность

- Служебный registration endpoint не использует пользовательские роли.
- Полный список кандидатов доступен только серверно проверенному
  `wispo_admin`.
- Этап не содержит API активации или rollback, поэтому их нельзя вызвать
  прямым запросом в обход интерфейса.
- Служебный отчёт о фактической выкладке защищён тем же release token и не
  доступен пользовательскому интерфейсу.
- Номер версии, repository URL и runtime URL проходят строгую валидацию.
- Runtime URL допускает только HTTP(S); локальные и исполняемые схемы запрещены.
- Ошибки API не возвращают release token, переменные окружения или внутренние
  логи сборки.
- Успешные регистрации и безопасные сведения об отклонённых semantic-проверках
  отражаются в audit без token и полного manifest.

## Проверка результата

Обязательный сценарий на Skinova:

1. локальная служебная команда регистрирует v1 повторно и получает тот же
   результат без дубликата;
2. регистрация версии с конфликтующим digest отклоняется;
3. кандидат не меняет публичный сайт;
4. администратор Wispo видит кандидата и его preview URL, если его передал CI;
5. владелец видит только текущую версию; менеджер не видит управление;
6. регистрация кандидата не меняет текущую версию и каталог сайта;
7. preflight до выкладки не меняет данные, а после отдельного служебного
   отчёта о локальной выкладке public manifest возвращает
   текущий Skinova v1 и поддерживаемые шаблоны;
8. preview и public используют единый resolver текущей сборки;
9. существующие Skinova contract/E2E проверки продолжают проходить;
10. в интерфейсе нет действий, создающих ложное впечатление физической
    активации или rollback.

## Следующий этап: физическая публикация

Отдельная спецификация этапа 5 должна определить сборку и хранение
неизменяемого артефакта каждой версии, preview deployment, очередь публикации,
атомарный switch, healthcheck и rollback. Только после появления этого контура
текущая диагностическая ссылка сайта может стать управляемым active pointer.

## Документирование и выпуск

Реализация фиксируется в `docs/change-log.md` и дополняет
`docs/react-site-architecture.md`. Коммит и push выполняются только после
локальной проверки и отдельного подтверждения владельца. VDS, `main` и внешняя
БД в рамках разработки не изменяются.
