# План локальной реализации ревизий Wispo CMS

Основание: [утверждённая спецификация](../specs/2026-09-18-cms-revisions-approval-design.md). Никаких коммитов, деплоя, действий на VDS или глобальных обновлений окружения.

## 1. Общий механизм

- Тестами зафиксировать переходы черновика: новая версия не наследует одобрение; согласование относится к точному ID; сотрудник не одобряет; публикация чужого сайта и устаревшего ID отклоняется; откат создаёт новую версию.
- Добавить модели неизменяемых снимков, ресурса с указателями и событий переходов. Миграция только аддитивная, без замены действующих маршрутов.
- Реализовать транзакционные операции создания ревизии, отправки, возврата с причиной, одобрения, публикации и восстановления. Проверить параллельное сохранение и повтор запроса.
- Прогнать тесты, сборку и миграцию в изолированной локальной PostgreSQL; проверить схему и отсутствие изменения публичных ответов.

## 2. Существующий контент

- Инвентаризировать все пути сохранения и публичного чтения: статьи, категории, авторы, страницы, баннеры, SEO, общие данные, медиа-метаданные, header/footer, приватность и настройки.
- Сначала переключить статьи: доказать тестом, что правка опубликованной статьи остаётся черновиком; одобрение точной версии и публикация меняют публичное состояние атомарно. Сохранить существующую историю версий и расписание без обхода нового контроля.
- По одному подключить остальные сущности и их публичные потребители. Для каждого типа проверить черновик, preview, права, согласование, публикацию, откат и зависимости. До завершения инвентаря общий этап не считать готовым.
- Мигрировать существующее состояние без догадок о старой опубликованной версии; спорные записи отмечать для сверки с резервной копией.

## 3. Код, редактируемый в CMS

- Ввести шаблон и чанк как управляемые ресурсы с HTML и параметрами. Тестировать сохранение снимка, ссылки на медиа, места использования, изоляцию сайтов и права разработчика.
- Подключить HTML-редактор, сравнение версий и preview на том же renderer, что публичный вывод. CSS/JavaScript включать в этот же процесс лишь если они доступны в CMS.
- Проверить безопасность подстановок и сборки, согласование владельцем точной версии, одновременное обновление всех мест использования и сохранение старого release при ошибке.

## 4. Проверка и журнал

- На каждом шаге: тест падает на отсутствующем поведении, затем проходит; весь API test/build, web typecheck, миграция и реальные сценарии с владельцем, сотрудником и посторонним на локальной копии.
- В `IMPLEMENTATION_LOG.md` отмечать реализованным только проверенное; отдельно перечислять оставшиеся пути и ограничения. Вопрос лимита хранимых версий — будущий, автоматической очистки нет.
