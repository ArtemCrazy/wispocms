# Wispo CMS: граница данных CMS и React-кода сайтов

Дата решения: 02.10.2026. Статус: утверждено, реализовано локально в ветке
`codex/access-control-v2`. VDS и `main` не изменяются.

## Основной принцип

Wispo CMS не является HTML/PHP-редактором и не хранит исходный код React-компонентов.
Она управляет содержимым сайта и выбором заранее реализованных вариантов отображения.

- React-компоненты, их разметка, стили, схемы данных и логика находятся в Git.
- У каждого сайта с уникальной вёрсткой — отдельный репозиторий. Если несколько
  сайтов действительно используют одну кодовую базу, допустим общий репозиторий
  темы с независимыми конфигурациями и релизами.
- CMS хранит данные экземпляров компонентов: тексты, изображения, ссылки,
  параметры отображения, порядок блоков и назначение готового шаблона.
- CMS не предоставляет поля, права, маршруты или API для редактирования HTML,
  PHP, JSX/TSX, CSS либо другого исходного кода.

## Что версионирует CMS

Новая неизменяемая ревизия создаётся при изменении данных, доступных в CMS:

- статей, страниц, категорий и авторов;
- баннеров и других экземпляров компонентов;
- переменных, SEO, шапки, подвала, поиска и политики;
- привязок готовых шаблонов и конфигурации областей сайта;
- медиа-метаданных и других полей, которыми управляет редактор.

Согласование и публикация относятся к конкретной ревизии данных. Изменение
одобренного черновика создаёт новую ревизию и при включённом
`requiresApproval` требует повторного согласования.

Исторические строки прежних типов `template` и `chunk` в таблицах ревизий не
удаляются миграцией, чтобы не терять данные. Однако новые кодовые ревизии этих
типов CMS не создаёт, и публичного API для них нет.

## Что версионирует Git

Git хранит изменения исходного кода сайта:

- добавление нового поля в React-компонент;
- изменение HTML/JSX-разметки, CSS и поведения;
- изменение схемы входных данных компонента;
- создание нового компонента или варианта шаблона;
- изменение интеграции сайта с CMS.

Откат кода выполняется релизом предыдущего commit/tag соответствующего сайта.
Откат контента выполняется через историю ревизий CMS. Эти два механизма не
смешиваются и не создают копии исходного кода в базе CMS.

## Пример: в баннер добавляется кнопка

1. Разработчик или AI-агент меняет React-компонент баннера и его схему данных в
   репозитории конкретного сайта.
2. Изменение проходит обычную проверку и выпускается как новый Git-релиз сайта.
3. После обновления интеграции CMS показывает новые поля кнопки: текст, ссылку и
   при необходимости вариант оформления.
4. Контент-менеджер заполняет поля. CMS создаёт ревизию данных баннера.
5. Ревизия публикуется напрямую либо после согласования — в зависимости от
   `requiresApproval` пользователя.

Если изменение совместимо назад, существующие баннеры продолжают работать с
пустой или скрытой кнопкой. Если совместимость невозможна, миграция данных и
порядок выкладки должны быть частью релиза сайта.

## Шаблоны и «чанки» в новой модели

Термин «шаблон» в интерфейсе означает зарегистрированный React-вариант страницы
или общей области, например `article-list`, `compact-header` или
`system-policy`. CMS хранит ключ, версию и JSON-конфигурацию, но не исходный код.

То, что раньше обсуждалось как «экземпляр чанка», является экземпляром React-
компонента с данными. Например, два баннера используют один компонент, но имеют
разные заголовки, изображения и ссылки. Изменение данных одного экземпляра не
создаёт новую версию компонента и не меняет другие экземпляры.

## Права

- Администратор Wispo имеет полный платформенный доступ.
- Владелец сайта имеет максимальные права внутри назначенного сайта, включая
  выбор зарегистрированных шаблонов, но не редактирует исходный код.
- Контент-менеджер редактирует данные назначенных сайтов. Флаг
  `requiresApproval` определяет, нужна ли владельцу/администратору проверка его
  ревизий перед публикацией.
- Отдельного права `canEditCode` и роли разработчика в CMS нет.

## Реестр frontend-пакетов

Связь сайта с конкретной сборкой реализована через неизменяемые версии
frontend-пакета. Реестр хранит стабильный `packageId`, `packageVersion`, Git
revision, release digest, безопасный manifest с описанием поддерживаемых
template identity и два указателя сайта: пакет и его фактически развёрнутую
версию. Исходный React-код и build-артефакты в БД не сохраняются.

Release pipeline выполняет операции раздельно:

1. `register` регистрирует неизменяемого кандидата. Повтор с тем же содержимым
   идемпотентен, а повтор той же версии с другим digest отклоняется.
2. `preflight` только проверяет совместимость кандидата с типом сайта,
   назначенными шаблонами и доступным runtime. Указатели сайта и публичный
   каталог эта операция не меняет.
3. Физическую выкладку React-приложения выполняет внешний deployment-процесс.
   CMS не переключает файлы, контейнеры или Git revision.
4. Только после успешной физической выкладки `report-deployed` фиксирует
   правдивый указатель текущей версии. После этого public API начинает
   возвращать новую package identity.

В CMS это состояние доступно только для чтения: владелец видит текущую версию,
администратор Wispo — текущую версию и совместимых кандидатов. Контент-менеджеру
раздел недоступен. Ручной загрузки manifest, активации и rollback из интерфейса
нет. Откат остаётся отдельным deployment предыдущего неизменяемого артефакта с
последующим `report-deployed`.

## Локальная интеграционная проверка Skinova

3 октября 2026 года сценарий проверен локально на отдельной одноразовой
PostgreSQL. На пустой БД выполнен штатный `bootstrap-local-database`, затем все
51 зарегистрированная TypeORM-миграция; рабочая локальная БД и OpenServer не
использовались. Проверка доказала:

- регистрацию Skinova и идемпотентный повтор без второй версии;
- конфликт той же `packageVersion` при изменённом release digest;
- отсутствие package identity в public manifest и public site catalog после
  `register` и `preflight`, а также неизменность каталога назначенных шаблонов
  при `register`, `preflight` и `report-deployed`;
- появление `skinova-media@1` в обоих публичных ответах только после
  `report-deployed`;
- корректное legacy-состояние с `NULL`-указателями и честный статус `mismatch`
  без подмены текущей версии;
- реальный release CLI из чистого временного Git snapshot с ephemeral commit,
  без обхода защиты от dirty release inputs;
- read-only browser workflow панели пакета на изолированном локальном web.

Это проверка локальной реализации. Commit рабочей ветки, push, физическая
выкладка, активация артефактов и rollback в рамках этой проверки не выполнялись.
