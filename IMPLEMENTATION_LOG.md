# Wispo CMS — решения и реализация

Здесь отдельно фиксируются согласованные требования и уже реализованные, проверенные изменения. Требование не считается реализованным, пока это не подтверждено проверкой локальной версии.

## Согласованная целевая модель

### Права пользователей — 2026-09-18

| Роль | Область и права |
| --- | --- |
| Администратор Wispo | Полный доступ ко всем сайтам, коду и пользователям. Создаёт любые аккаунты и назначает их на один или несколько сайтов. |
| Владелец сайта (администратор пространства из ТЗ) | Полные права только внутри своего сайта: контент, код, одобрение, публикация и управление пользователями. Создаёт разработчиков и контент-менеджеров только для своего сайта. |
| Менеджер Wispo | Редактирует контент назначенных администратором Wispo сайтов. После одобрения владельцем публикует утверждённую версию. Код и управление пользователями недоступны. |
| Контент-менеджер владельца | Те же права на контент и тот же процесс одобрения, но строго для одного сайта владельца. |
| Разработчик Wispo | Редактирует контент и код назначенных администратором Wispo сайтов. После одобрения владельцем публикует утверждённые изменения. Пользователями не управляет. |
| Разработчик владельца | Те же права разработчика, но строго для одного сайта владельца. |

Для менеджеров, контент-менеджеров и разработчиков одобряется конкретная версия изменения. Любая правка после одобрения требует повторной проверки; сохранение черновика не публикует его. Правило распространяется и на контент, и на код разработчика.

Ограничение сайта проверяется сервером при каждом запросе, включая прямой URL и API. Аккаунты сотрудников Wispo и пользователей владельца не объединяются; созданный владельцем аккаунт нельзя расширить на другие сайты. Email уникален во всей CMS. Совпадение личности по разным email система не проверяет.

Отдельную роль клиента-согласующего пока не вводим: проверку выполняет владелец сайта. В будущем владелец сможет задавать требование одобрения отдельно для пользователя на своём сайте; в первом этапе все перечисленные сотрудники проходят одобрение.

### Версионность и согласование — 2026-09-18

**Статус: архитектура согласована, реализация ещё не завершена.** Версионируется всё, что уполномоченный пользователь редактирует внутри CMS: данные публикаций, переменные, настройки контента и исходный HTML/CSS/JavaScript шаблонов и чанков, когда соответствующий редактор доступен в CMS. Исходники приложения вне CMS версионируются через Git и резервные копии, а не через этот механизм.

Каждое сохранение создаёт неизменяемую ревизию. Черновая и опубликованная ревизии разделены; одобрение владельца относится к конкретной ревизии, последующая правка его не наследует. Сотрудник может публиковать только утверждённую ревизию при наличии соответствующего права. Откат создаёт новую ревизию, сохраняя прежнюю историю. Изменение общего чанка перед одобрением должно показывать затронутые места и preview.

**На будущее:** оценить ограничение общего числа хранимых ревизий и политику хранения. Пока лимит не задан и автоматическое удаление истории не вводится; при проектировании учесть объём БД, медиа, опубликованные версии, аудит и возможность восстановления. Решение о конкретном лимите и сроке хранения принять отдельно.

## Реализовано и проверено

### Этап 1. Локальные роли, учётные записи и границы сайтов — 2026-09-18

**Статус: реализовано в локальной копии. Коммита нет.** Изменения не отправлялись на VDS и не вносились в `main`.

- В модели данных появились роли владельца сайта, менеджера Wispo, контент-менеджера сайта, разработчика Wispo и разработчика сайта. Для учётки хранится её тип (Wispo или локальная учётка сайта), а для назначений — точный список сайтов. Email остаётся уникальным во всей CMS.
- Администратор Wispo может создавать эти учётки и назначать сотрудника Wispo на несколько сайтов. Локальная учётка владельца или его сотрудника ограничена одним сайтом; старые маршруты назначения целого рабочего пространства не расширяют новые учётки.
- Владелец сайта через отдельные API-маршруты и экран CMS может просматривать и создавать своих контент-менеджеров и разработчиков, включать и отключать их доступ. Создать пользователя для соседнего сайта или второго владельца через этот маршрут нельзя.
- Проверка принадлежности к конкретному сайту добавлена в сессию и серверные операции контента, жизненного цикла публикаций, политики конфиденциальности и аудита. Смена привязки шаблона шапки, подвала и страницы 404 требует права на код.
- Аддитивная миграция `SiteScopedRoles1790017200000` применена только к локальной PostgreSQL. Старым назначениям доступ к сайтам автоматически не выдавался.

**Проверка:** 55 наборов / 302 API-теста прошли; сборка API и проверка TypeScript веб-приложения прошли; локальные API и веб ответили `200`. Визуальная проверка нового экрана в браузере пока не завершена: инструмент просмотра завершился с ошибкой.

### Этап 2а. Внутреннее ядро ревизий — 2026-09-18

**Статус: реализовано и проверено локально только ядро; пользовательский процесс ещё не подключён.** Коммитов и изменений на VDS нет.

- Добавлены общие ресурсы, неизменяемые снимки и события истории с отдельными указателями черновой, одобренной и опубликованной версии. Миграции `CmsRevisionLedger1790103600000` и `ProtectCmsRevisionHistory1790107200000` применены только к локальной PostgreSQL. Ограничения БД связывают указатели с версиями того же ресурса; триггеры запрещают изменение и удаление записей истории.
- Внутренний сервис проверяет сайт и роль, сохраняет черновик с защитой от параллельной правки, отправляет на проверку, одобряет, возвращает с причиной, публикует утверждённый ID, показывает историю и восстанавливает старый снимок как новую неодобренную редакцию. Сотрудник без права кода не может создавать или читать ревизию чанка.
- Проверка: полный API-набор — 57 прошедших наборов / 318 тестов, один набор и один тест пропущены по условию окружения; сборка API прошла. Отдельный тест с реальной локальной PostgreSQL выполнил сохранение, одобрение, публикацию, проверку неизменяемости и откатил все тестовые записи. Локальные API и веб ответили `200`.

В существующий снимок истории статьи добавлены ранее пропущенные поля Open Graph и структурированных данных. Это исправляет полноту новых снимков, но не подключает общие ревизии к опубликованной статье.

**На момент завершения этапа 2а:** сервис ещё не был связан со старыми маршрутами сохранения, публичным чтением, preview, расписанием и редактором HTML. Подключение черновиков статей описано ниже; полную версионность и согласование пока нельзя считать готовыми.

### Этап 2б. Черновики опубликованных статей — 2026-09-18

**Статус: частично реализовано и проверено локально. Процесс публикации ещё не готов.** Коммитов, изменений на VDS и в ветке `main` нет.

- При сохранении текста или параметров уже опубликованной/скрытой статьи создаётся новая неизменяемая ревизия. При первой правке исходная публичная строка импортируется как базовая версия; само сохранение не меняет публичную строку статьи. Для текста проверяется ожидаемый номер редакции, для обеих операций — указатель текущей черновой ревизии.
- Список статей в CMS и авторизованный preview показывают последнюю черновую редакцию и идентификаторы версий. Публичные маршруты продолжают читать прежнюю строку статьи.
- Публикация в ядре умеет применить утверждённый снимок к публичной строке в одной транзакции с переключением указателя. На момент этапа 2б этот callback ещё не был подключён к маршруту публикации статьи; подключение описано ниже. Также исправлена обязательная инъекция репозиториев сервиса ревизий.
- Проверка: тесты сначала воспроизвели отсутствие разделения черновика и публичной статьи, затем прошли; полный локальный API-набор — 57 наборов / 325 тестов, ещё два условно пропущены; сборка API прошла. Два интеграционных теста ревизий на локальной PostgreSQL прошли с откатом данных. Локальный API ответил `200`.

**На момент завершения этапа 2б:** старые действия смены редакционного/публикационного статуса, восстановление прежней истории и планировщик ещё обходили новый ledger. В интерфейсе не было команд согласования; черновик нельзя было считать выпущенным. Изменения серверной части следующего этапа описаны ниже.

### Этап 2в. Серверное согласование и выпуск версии статьи — 2026-09-18

**Статус: серверный процесс для текста и основных параметров уже опубликованной статьи реализован и проверен локально; пользовательский интерфейс и остальные пути редактирования ещё не готовы.** Коммитов, изменений на VDS и в `main` нет.

- Авторизованные API-маршруты показывают текущую ревизию и историю, отправляют конкретный ID на проверку, позволяют владельцу/администратору одобрить его или вернуть с причиной, а сотруднику — выпустить только утверждённый ID. Восстановление исторического снимка создаёт новый черновик с проверкой ID текущего черновика.
- При выпуске статья проверяется против сохранённой исходной публичной версии; если публичная строка успела измениться, выпуск отклоняется. Снимок валидируется, связи с рубрикой/автором/медиа и шаблоном проверяются, адресное перенаправление, публичная строка, старая история статьи, аудит и указатель опубликованной ревизии обновляются в одной транзакции. В снимке и применении учтены OG-поля и дата публикации; старые снимки без даты принимаются.
- Для статьи, переведённой на ledger, старые ручные переходы статусов, восстановление через прежнюю историю или корзину и создание старого расписания отклоняются. Уже запланированная старая операция отмечается ошибкой, а не меняет публичную статью. Прямое удаление такой статьи заблокировано до отдельного процесса архивирования. CMS preview подтягивает рубрику, автора и изображения из черновика, а не из старой публичной строки.
- Проверка: полный API-набор — 58 прошедших наборов / 344 теста, 3 условно пропущены; сборка API, TypeScript веб-приложения и проверка содержательных правил ESLint для затронутых файлов прошли. Три теста на реальной локальной PostgreSQL прошли с откатом; после них в `cms_revision_resources` осталось 0 записей. После перезапуска только локального API его health ответил `200`, новый защищённый маршрут — `401` без входа. Все четыре локальных контейнера в состоянии healthy.

**На момент этапа 2в:** в работающем интерфейсе ещё не было экрана отправки, одобрения и выпуска ревизий; сценарий с двумя реальными ролями в браузере не был проверен. Новые неопубликованные статьи, связи между статьями, восстановление удалённой статьи, расписание по ID утверждённой версии, другие сущности и шаблоны/чанки не переведены на этот процесс. Старую редакционную историю нельзя считать заменой нового ledger. Полный механизм для всей CMS не завершён.

### Этап 2г. Интерфейс версий статьи — 2026-09-18

**Статус: сценарий опубликованной статьи подтверждён в локальном браузере под менеджером и владельцем.** Всё выполнено только локально, без коммитов и изменений на VDS.

- Для статьи с новым журналом версий интерфейс показывает номер и состояние текущей ревизии, отправку владельцу, возврат с причиной, одобрение конкретной версии и выпуск только одобренной версии. Менеджеру доступна публикация после одобрения владельцем; сам одобрить он не может. Для опубликованной статьи добавлена ссылка на защищённый предпросмотр черновика рядом со ссылкой на публичный вариант.
- В истории видны неизменяемые версии CMS; восстановление создаёт новый черновик. Старые несовместимые кнопки смены статуса, расписания, восстановления прежней истории и удаления скрыты для статьи, подключённой к журналу. Массовые старые операции блокируются, если в выборке есть статья с новой историей. Для ещё не переведённых статей старый интерфейс пока сохранён.
- Тесты расчёта действий по состоянию ревизии и обработки пустого успешного ответа API прошли. Полный API-набор: 58 наборов / 344 теста прошли, 1 набор / 3 теста пропущены по условию окружения. TypeScript и ESLint изменённых фронтенд-файлов прошли. Production-сборка Next.js на проектной Node 24 прошла после остановки локального dev-сервера: одновременная запись двух процессов в общий `.next` вызывала ошибку prerender. Локальные веб и API после перезапуска ответили HTTP 200.
- Playwright установлен как dev-зависимость только `apps/web`; тест `test/article-revision-workflow.spec.ts` прошёл в локальном Chrome с двумя независимыми браузерными сессиями и отдельной временной копией БД. Менеджер изменил опубликованную статью, отправил точную ревизию владельцу, не увидел кнопку одобрения; владелец одобрил; менеджер опубликовал. Публичный API до публикации отдавал прежний заголовок, после — новый. Сделаны и просмотрены снимки экрана владельца и узкого экрана менеджера. Встроенный Chromium не загрузился из-за тайм-аута CDN, поэтому использован уже установленный Chrome. Тест изменяет данные и защищён явным opt-in `WISPO_E2E_ISOLATED_DB=wispo_cms_e2e`; запускать его можно только с отдельной временной БД.
- Браузерный тест выявил и позволил исправить две ошибки интерфейса: пустой успешный ответ API оставлял бесконечную надпись «Загружаем состояние согласования…»; после `await` обработчик сохранения терял `event.currentTarget`, и `FormData` не создавалась. Исправления проверены тем же тестом. TypeScript, ESLint и production-сборка Next.js прошли повторно. Возврат на доработку, конкурирующее редактирование/конфликт версии и отдельные мобильные взаимодействия ещё нужно проверить отдельными сценариями; полная сверка дизайна с ТЗ не проводилась. Временные API/Redis-контейнеры и БД `wispo_cms_e2e` удалены; в основной БД нет E2E-пользователей, E2E-статей и ревизий.

### Этап 2д. Проверка возврата и защита от конкурирующего редактирования — 2026-09-18

**Статус: проверено в локальной копии.** Коммитов, изменений на VDS и в `main` нет; дизайн не менялся.

- При возврате опубликованной статьи на доработку исправленная версия повторно отправляется владельцу, одобряется и публикуется как отдельная ревизия. Браузерный сценарий это подтвердил.
- Автосохранение текста из устаревшей вкладки получает конфликт и оставляет введённый текст в редакторе. Сохранение параметров опубликованной статьи теперь отправляет ID черновика, который видел редактор; сервер отклоняет устаревший ID с `409` до записи новой ревизии. После собственного автосохранения текста редактор использует ID созданной им ревизии. При первой правке без черновика передаётся `null`.
- Проверка: 3 браузерных сценария Playwright в локальном Chrome на отдельной временной копии БД прошли; полный API-набор — 58 наборов / 345 тестов прошли, 1 набор / 3 теста пропущены; сборка API, проверка TypeScript веб-приложения и ESLint затронутых веб-файлов прошли. Временные веб/API/Redis и БД `wispo_cms_e2e` удалены; основная локальная БД не использовалась для E2E-записей.

**Граница этапа:** защита касается опубликованной статьи и её текста/параметров. Она не заменяет согласование для других сущностей CMS. Полная визуальная сверка дизайна остаётся отдельной задачей.

### Этап 2е. Одобрение просмотренной версии и точный предпросмотр статьи — 2026-09-18

**Статус: реализовано и проверено локально.** Коммитов, изменений на VDS и в `main` нет.

- Перед действием над статьёй интерфейс сверяет ID открытой ревизии с текущим ID на сервере. Если после открытия появилась новая версия, действие не выполняется; повторный клик не переключает незаметно открытый экран на новую версию. Владелец должен открыть материал заново и проверить его.
- Ссылка предпросмотра содержит ID конкретной ревизии. Сохранение следующего черновика не меняет содержимое ранее открытой ссылки. Сервер возвращает исторический снимок только в пределах указанного сайта и статьи.
- Проверка: регрессионные браузерные тесты сначала воспроизвели одобрение непросмотренной версии и смену содержимого старой ссылки; после исправления общий набор из 7 браузерных сценариев статей и страниц прошёл. Полный API-набор — 60 успешных наборов / 357 тестов, 3 условно пропущены; сборка API, TypeScript веб-приложения и ESLint затронутых файлов прошли без ошибок.

**Граница этапа:** фиксируется снимок самой статьи; связанные баннеры, общие данные и остальное окружение preview пока могут брать текущее состояние.
