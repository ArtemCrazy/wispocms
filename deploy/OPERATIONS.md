# Wispo CMS: эксплуатация preview-сервера

## Размещение

- проект: `/opt/wispo-cms`;
- web: контейнер `wispo-cms-preview-web-1`, локальный порт `3300`;
- API: контейнер `wispo-cms-preview-api-1`, локальный порт `4300`;
- PostgreSQL: контейнер `wispo-cms-preview-postgres-1`;
- публичный адрес: `https://wispo-cms.45.12.74.66.nip.io`;
- nginx-конфигурация: `/www/server/panel/vhost/nginx/wispo-cms-preview.conf`;
- TLS-сертификат: `/etc/letsencrypt/live/wispo-cms.45.12.74.66.nip.io/`.

Web и API запускаются внутри контейнеров от пользователя `node` с UID/GID
`1000:1000`. Docker volume медиатеки должен принадлежать этому пользователю.
После переноса или ручного восстановления проверить:

```sh
docker exec wispo-cms-preview-api-1 id
docker exec wispo-cms-preview-api-1 ls -ldn /data/media
```

Ожидаемый владелец `/data/media`: `1000:1000`.

## Изоляция контейнеров

Web и API запускаются с read-only корневой файловой системой, без Linux
capabilities и с `no-new-privileges`. Временные файлы размещаются в отдельном
`tmpfs` `/tmp`. API может записывать только в подключённый volume
`/data/media`, а web — в `tmpfs` кэша `/app/apps/web/.next/cache`.

Проверка действующих ограничений:

```sh
docker inspect wispo-cms-preview-api-1 wispo-cms-preview-web-1 \
  --format '{{.Name}} readonly={{.HostConfig.ReadonlyRootfs}} capdrop={{json .HostConfig.CapDrop}} security={{json .HostConfig.SecurityOpt}}'
```

Ожидается `readonly=true`, `capdrop=["ALL"]` и
`security=["no-new-privileges:true"]` для обоих контейнеров.

## Перезапуск

```sh
cd /opt/wispo-cms
docker compose --env-file deploy/.env.preview -f deploy/compose.preview.yaml up -d
```

## Миграции базы

API запускает ожидающие TypeORM-миграции автоматически до начала обработки
запросов. Автоматическая синхронизация схемы отключена: `DB_SYNCHRONIZE` не
используется. Все изменения структуры базы должны оформляться новой миграцией в
`apps/api/src/database/migrations` и проверяться сначала на отдельной пустой
базе.

Стартовая миграция умеет безопасно принять уже существующую полную схему как
baseline. Если найдена только часть ожидаемых таблиц, она завершает запуск с
ошибкой и ничего не достраивает. Перед выкладкой миграций необходимо сделать
свежий дамп базы. Откат стартовой миграции удаляет все таблицы приложения и не
должен выполняться на рабочей базе.

## Автоматический мониторинг

Скрипт `/opt/wispo-cms/deploy/monitor-preview.sh` проверяет состояние трёх
контейнеров, публичные HTTPS-адреса, срок действия TLS-сертификата, заполнение
диска и свежесть резервных копий базы и медиатеки. Он не перезапускает сервисы
и не удаляет данные. Порог диска — 85%, минимальный остаток TLS — 14 дней,
максимальный возраст резервной копии — 30 часов.

Запуск вручную:

```sh
/opt/wispo-cms/deploy/monitor-preview.sh
```

Плановая проверка выполняется каждые 5 минут. Журнал:
`/var/log/wispo-cms-monitor.log`. Ошибки также отправляются в системный журнал
с тегом `wispo-cms-monitor`.

Пороги можно изменить переменными `WISPO_DISK_LIMIT_PERCENT`,
`WISPO_BACKUP_MAX_AGE_MINUTES` и `WISPO_TLS_MIN_SECONDS`. Для изолированной
проверки ошибочного сценария отправку в syslog можно отключить переменной
`WISPO_MONITOR_SYSLOG=false`.

## Резервные копии базы

Скрипт `/opt/wispo-cms/deploy/backup-preview.sh` создаёт сжатый дамп базы и
SHA-256 checksum. Архив сначала записывается во временный файл и становится
доступным только после успешной проверки gzip.

Запуск вручную:

```sh
/opt/wispo-cms/deploy/backup-preview.sh
```

Архивы: `/root/wispo-cms-backups/database/`.

Журнал ежедневного запуска: `/var/log/wispo-cms-backup.log`.

Автоматическое удаление старых архивов намеренно не включено. Очистка должна
выполняться отдельно после проверки доступного места и подтверждения владельца.

## Резервные копии медиатеки

Скрипт `/opt/wispo-cms/deploy/backup-media-preview.sh` архивирует содержимое
Docker volume с `/data/media`, проверяет целостность gzip и tar, создаёт SHA-256
checksum и небольшой manifest с количеством файлов и размером архива.

Запуск вручную:

```sh
/opt/wispo-cms/deploy/backup-media-preview.sh
```

Архивы: `/root/wispo-cms-backups/media/`.

Журнал ежедневного запуска: `/var/log/wispo-cms-media-backup.log`.

Для проверки архива использовать обе команды:

```sh
sha256sum -c /root/wispo-cms-backups/media/<archive>.sha256
tar -tzf /root/wispo-cms-backups/media/<archive>
```

Восстановление медиатеки перезаписывает файлы действующего volume. Его можно
выполнять только после отдельного подтверждения и создания свежей копии текущей
медиатеки.

## HTTPS

HTTP используется только для проверки ACME-запросов и перенаправляет остальные
запросы на HTTPS. Продление сертификата выполняет системный `certbot.timer`.

Каноническая nginx-конфигурация проекта хранится в
`/opt/wispo-cms/deploy/nginx.preview.conf`. Она включает HSTS, запрет MIME
sniffing, защиту от встраивания в чужой iframe, ограничение browser permissions
и скрытие служебных заголовков фреймворков. Перед заменой рабочего конфига
обязательно сохранить его копию и выполнить `nginx -t`.

API принимает изменяющие browser-запросы только с источников из `WEB_ORIGIN`.
Несколько разрешённых источников указываются через запятую. Серверные запросы
без заголовка `Origin` остаются доступными для эксплуатации и интеграций.

Проверка продления без выпуска нового сертификата:

```sh
certbot renew --dry-run
```

### Пользовательские домены

CMS нормализует домен, не считает его подключённым при одном сохранении и
разрешает host-based routing только после успешной DNS-проверки. Допустимые
A/AAAA-адреса и CNAME-цели задаются через `PUBLIC_DOMAIN_TARGETS`; служебные
CMS/API-hostnames перечисляются в `WISPO_RESERVED_HOSTS`.

Product-side routing готов для `/`, `/articles/<slug>`, `/categories/<slug>`,
`/pages/<slug>`, `/robots.txt` и `/sitemap.xml`. Единственная внешняя
предпосылка для нового домена — оператор инфраструктуры должен добавить этот
hostname в ingress, направить DNS на одну из `PUBLIC_DOMAIN_TARGETS` и выпустить
TLS-сертификат. Текущий nginx-конфиг и сертификат обслуживают только
`wispo-cms.45.12.74.66.nip.io`; CMS не меняет чужой DNS и не выпускает
сертификаты автоматически.

## Восстановление

Перед восстановлением сначала проверить checksum выбранного архива:

```sh
sha256sum -c /root/wispo-cms-backups/database/<archive>.sha256
```

Восстановление перезаписывает данные и выполняется только после отдельного
подтверждения и дополнительного актуального дампа.

## Репетиция восстановления

Последняя изолированная репетиция выполнена 23 августа 2026 года. Проверены
реальное распаковывание последнего дампа PostgreSQL и архива медиатеки, точное
совпадение схемы, данных, количества файлов и SHA-256 содержимого. API успешно
запущен на восстановленной базе и отдельном media volume; публичные данные и
медиафайл прочитаны через HTTP.

Репетицию всегда выполнять в базе и Docker volume с отдельными явными именами.
До проверки не подключать к ним рабочие контейнеры и nginx. После успешного
теста остановить временный API, удалить только созданные для репетиции базу и
volume и повторно запустить `/opt/wispo-cms/deploy/monitor-preview.sh`.

Рекомендуемая периодичность — после изменения формата резервных копий или схемы
БД и не реже одного раза в квартал.

## Приёмочный E2E-прогон

Последний изолированный E2E-прогон выполнен 23 августа 2026 года на отдельном
стеке PostgreSQL, API, web и media volume. Проверены вход администратора,
переход из главной в раздел статей, создание черновика, перевод на согласование,
публикация, запись истории статусов и появление статьи в публичных API и web.

Тестовый стек не должен подключаться к рабочей Docker-сети или использовать
рабочую базу. После прогона необходимо удалить только его явно именованные
контейнеры, volumes и networks, закрыть SSH-туннель и выполнить штатный
`monitor-preview.sh` для действующего окружения.

## Адаптивная приёмка

Последняя изолированная визуальная проверка выполнена 23 августа 2026 года в
реальном браузере на размерах 1440×900, 1024×768 и 390×844. Проверены экран
входа, навигация рабочего пространства, список статей, форма создания
материала и публичная страница сайта. Общей горизонтальной прокрутки нет;
широкая таблица статей на мобильном экране прокручивается только внутри своего
контейнера.

Для повторной проверки использовать отдельные PostgreSQL, API, web, media
volume и Docker-сети, не подключённые к production. После проверки удалить
только явно именованные временные объекты, закрыть туннель и повторно выполнить
`/opt/wispo-cms/deploy/monitor-preview.sh`.

## Базовая проверка производительности

Последний безопасный GET-only прогон выполнен 23 августа 2026 года с
параллельностью 8. Внутри production-стека получено 100 успешных ответов из
100: `p95` для `/api/health` — 44,6 мс, для публичного API сайта — 97,1 мс.
Через полный HTTPS-контур получено 150 успешных ответов из 150: `p95` для
health — 774,6 мс, публичного API — 74,8 мс, публичной страницы — 77,1 мс.
Контейнеры после прогона остались healthy, ошибок приложения не зафиксировано.

Это базовый smoke, а не расчёт максимальной пропускной способности. Повторять
его только GET-запросами, без форм, авторизации и изменения рабочих данных.

## Серверная SEO-выдача

С 24 августа 2026 года публичные главная, статьи и обычные страницы
рендерятся на сервере. Исходный HTML должен сразу содержать заголовок, основной
текст, `title`, description, robots, canonical и Open Graph без ожидания
выполнения JavaScript.

После каждого изменения публичного рендера проверять как минимум:

```sh
curl -fsS https://wispo-cms.45.12.74.66.nip.io/preview/wispo-media
```

В ответе не должно быть загрузочной заглушки `Загружаем опубликованный сайт`,
а название и описание сайта должны присутствовать в исходном HTML. Затем
нужно открыть страницу в браузере и убедиться, что клиентские элементы, включая
форму обратной связи, успешно гидратировались без ошибок консоли.
