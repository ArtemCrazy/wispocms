## Проверка и обслуживание

На VDS использовать **оба** Compose-файла: `compose.preview.yaml` задаёт
базовые сервисы, а `compose.customer.yaml` заменяет старые адреса и параметры
нового окружения. Один базовый файл запускать нельзя.

```sh
cd /opt/wispo-cms
docker compose --env-file deploy/.env.customer \
  -f deploy/compose.preview.yaml -f deploy/compose.customer.yaml ps
curl -fsS http://127.0.0.1:4300/api/health
curl -fsSI https://wispo-cms.129.101.122.78.nip.io/
/opt/wispo-cms/deploy/backup-customer.sh
```

При восстановлении или обновлении запускать `docker compose up -d` с теми же
двумя Compose-файлами только после проверки миграций, актуального архива и
состояния параллельной работы. Архивы имеют права root и не должны раздаваться
через веб-сервер.

## Резервирование и оставшиеся ограничения

- `deploy/backup-customer.sh` ежедневно запускается через
  `deploy/customer-backup.cron` в 03:17 UTC, создаёт дамп БД и архив медиа
  в `/root/wispo-cms-backups` на VDS. Текущая разовая независимая копия
  находится на ПК владельца. Автоматического бэкапа вне VDS **пока нет**:
  пользователь временно принял такой вариант и позже предоставит внешнее
  хранилище. До его настройки не удалять последнюю проверенную копию на ПК.
- Локальные архивы на VDS не имеют автоматического удаления. Следить за местом
  на диске и настроить ротацию только вместе с независимым хранилищем.
- Когда заказчик даст постоянный домен, обновить DNS, nginx, `PUBLIC_APP_URL`,
  `WEB_ORIGIN`, список служебных имён и OAuth redirect URI. Это не требуется
  для работы на текущем адресе.
- Перед включением почты получить клиентский SMTP и проверить доставку в
  реальный ящик. Перед приёмкой функции расшифровки проверить короткое видео
  целиком: скачивание аудио, Groq и сохранение текста.
- Не публиковать секреты, дампы и пользовательские документы в Git или в
  переписке задачи.
